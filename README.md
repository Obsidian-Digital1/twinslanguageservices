# Twins Language Services Website Plan

## Project Summary
This document outlines the website update and rebuild plan for **Twins Language Services** based on the current live website and the provided reference websites. The goal is to simplify the navigation, remove unpaid multilingual toggle functionality, preserve the core service positioning, and make the site more conversion-focused for bookings and direct inquiries.

## Primary Goals
- Keep the business positioned as a **language services provider** for interpretation, document translation, transcription, and related communication support.
- Remove the **English / Español translation toggle** from the current site.
- Replace the current loose quote-focused calls to action with a clearer **Booking** flow.
- Preserve the general homepage structure of the current website, while improving clarity, layout, and professionalism.
- Add a **Google Reviews** section to the homepage.
- Add **Google Maps** to the Contact page.
- Add footer social links for **LinkedIn, Instagram, and Facebook**.
- Use only **public domain** or clearly **commercial-use licensed** imagery.

## Services Page Plan
The Services page is the dedicated place to list what Twins Language Services offers, with clear next steps to schedule or ask questions.

## Services Page Purpose
- Present **translation and related language services** in one scannable layout (aligned with the business: interpretation, document work, and transcription—not only literal “translation” in the narrow sense).
- After the services list, drive visitors to **Booking** (Microsoft calendar) or **Contact Us** for anything that does not fit self-serve scheduling.

## Services Page Sections

### 1. Page intro
Short paragraph reinforcing professional language support for individuals, organizations, and specialized settings.

### 2. Translation and language services offered
List each offering with a concise description (rewrite in original copy per Content Direction). Suggested items to include:
- **Document translation** — written materials, certified or general (wording subject to client confirmation)
- **In-person interpreting**
- **Phone interpreting**
- **Video / virtual interpreting**
- **Transcription**
- **Court / legal interpretation** (positioning subject to client confirmation)

Optional: group into categories (e.g., spoken interpreting vs. written/transcription) if it improves scanability.

### 3. Next steps (below the services section)
Immediately under the services list, add a clear **dual path**:
- **Primary:** Link or button to **Booking** — same destination as the Booking page (Microsoft Bookings URL), labeled e.g. “Schedule online” or “Book an appointment.”
- **Secondary:** Link or button to **Contact Us** for questions, custom requests, or anything not handled via the calendar.

Do **not** embed a separate booking form on the Services page; scheduling goes through Microsoft Bookings via the Booking page or direct link.

## Booking Page Plan
The Booking page is **not** a form or embedded calendar on the site. It is a **styled landing strip** whose sole job is to send users to the **Microsoft Bookings** calendar the business already uses.

## Booking Page Purpose
- Reassure the visitor they are in the right place (“Schedule your service”).
- Provide one prominent, accessible **external link** that opens **Microsoft Bookings** (typically in a new tab).
- Optional short supporting copy (what to expect, business hours reminder if confirmed)—**no** fields, **no** iframe embed, **no** on-site booking UI.

## Booking Page Content (allowed)
- Headline and brief explanatory text
- Primary button or link: **Open scheduling calendar** (or equivalent)—points to the Microsoft Bookings URL provided by the client
- Optional secondary text link to **Contact Us** if they need help before booking

## Booking Page — explicitly out of scope
- On-page booking forms
- Email capture or service request forms on this page
- Embedded Microsoft Bookings widget or iframe (unless the client later requests it; default is **link only**)

## Hostinger deployment

- Use **Node.js 20 or 22** (Next.js 16 requires Node ≥ 20.9).
- Stay on **Next.js 16.2.12** until Hostinger’s glibc is ≥ 2.29. Next 16.3’s native SWC binary fails with `GLIBC_2.29 not found`.
- Do not install with `--no-optional`. Linux SWC binaries are optional dependencies and are required for `next build`.
- `.npmrc` tells pnpm to fetch Linux + Windows SWC packages even when the lockfile is updated on Windows.
